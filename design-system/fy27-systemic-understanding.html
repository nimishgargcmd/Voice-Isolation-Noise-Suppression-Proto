2 Theme-awareness model

Light/Dark is wired (ThemeProvider toggles .dark on <html>; persisted; system-default). But ~284 hardcoded colors across ~40 files mean dark mode is correct only on migrated/redesigned surfaces. New components consume --fy27-* tokens; legacy components get migrated as they're redesigned.

Three color patterns in the code
  • A · token semantic CSS vars / fy27-* utilities — theme-aware (≈5%, mostly ui/)
  • B · hardcoded hex/rgba — not theme-aware (≈85%)
  • C · local per-component THEMES object (≈10%, e.g. NativeInputBar)
The target

Everything new → pattern A using fy27-tokens. A component built on these tokens is correct in both modes with zero extra work. Migrate B/C in place when a surface is redesigned.

4 Evolution: current → FY27

The redesign keeps the IA, behavior, and state model and reinvents the visual language. The Mobile Meetings POR is the baseline: complete and state-rich, but visually conservative (flat monochrome glyphs, maroon end-call, grey utilitarian surfaces, dark pill name-chips, tile-arithmetic grids, text-heavy UFDs).

Keep (don't touch)
  • Information architecture & panel navigation
  • ActiveMeetingContext persistence model
  • Notification dedup/badge, recording, mic/agenda behavior
  • Multitasking dock + PiP carry-over
  • The full state coverage catalogued in §5
Reinvent
  • Type ramp, palette, surface/elevation, density
  • Iconography choices, motion grammar
  • Light + Dark as a first-class axis (tokens)
  • Glanceable surfaces over dense text cards
Mechanism — live versioned swap. current = today's components (baseline + default). Each MVP branch registers redesigned components under a version id; the resolver routes by active version (nearest-defined up the basedOn chain), so a version only declares what it changed. First example: MeetingHeader → HeaderV1 registered at mvp1. Switch live from the profile drawer. A slot can register Hidden to remove a component in a version.
