Retrospective · Rebuild Vision

If I rebuilt Udayan's Task Organizer from scratch

We shipped a working tool through ~40 rapid iterations. That very process exposed exactly where the architecture fights back. This is an honest post-mortem and a concrete plan for a v2 that would be faster to change, harder to break, and nicer to use.

Current: 1,434 lines · single HTML file
Migration flags: 4 ad-hoc localStorage keys
Tag defined in: 5 separate places

What actually hurt while building this

Every one of these is a symptom of a root cause, not a one-off. Ranked by how much friction it caused us in this session.

Modeling

The core thesis

If I could change only one thing, it would collapse most of the pain above.

Single source of truth → data-driven rendering.

Define tags, columns, and views as data. Render the UI from that data reactively. The "edit in 5 places" problem, the "refresh to see it" problem, and the focus-loss problem all dissolve because there is exactly one place to change a thing and the DOM updates itself.

Three principles

1. Data over markup. Tags/views are config objects. Every chip, filter, dropdown and column is generated.

2. Reactive over rebuild. A 3 KB renderer diffs the DOM. No more innerHTML nukes.

3. Versioned schema over ad-hoc flags. One ordered migration pipeline instead of four bespoke booleans.

What it buys you

• Add a tag = one line in TAGS.

• Edits appear instantly, no reload, no focus loss.

• New views (Board, Matrix) are ~30 lines, not a rewrite.

• Data migrations are safe, ordered, and testable.

Architecture

Keep the "one file you can double-click" ergonomics, but structure it properly inside.

Reactive state core replaces innerHTML rebuilds›

A single observable store. Mutations go through actions; the view subscribes and re-renders only what changed.

// one place owns truth; UI is a pure function of it
const store = createStore({
  schemaVersion: 5,
  tasks: [],
  views: { dashboard:{filters:[]}, compare:{columns:[[],[],[]]} },
  ui: { tab:'dashboard' }
})
store.subscribe(render)         // auto re-render
actions.toggleComplete(id)      // mutate via actions only

Implementation can be ~40 lines of vanilla (proxy + subscribe), or Alpine/Preact if we accept a tiny dependency.

Config-driven tags & views replaces 5× duplication›

Tags, their colors, and which axis they belong to are declared once. Chips, filters, the add-task form, compare pickers, and board columns are all generated from this.

const TAGS = {
  effort: { exclusive:true, options:[
    {id:'s', label:'Small effort',  hue:150},
    {id:'m', label:'Medium effort', hue:45},
    {id:'l', label:'Large effort',  hue:0} ]},
  category: { exclusive:false, options:[
    {id:'coordination', label:'Coordination', hue:265}, /* … */ ]}
}
// tints derived, not hand-picked:
// background: hsl(hue 70% 96%); text: hsl(hue 60% 40%)

Colors come from a single hue per tag via color-mix()/HSL — no more hand-tuning bgColor and discovering two tags clash.

Migration pipeline replaces cleanup_v1 / reorder_v4 …›

An ordered array of pure functions runs from the stored version up to current. Self-documenting history, runs exactly once each, trivially testable.

const migrations = [
  s => s,                                  // v0→1 base
  s => ({...s, tasks: dropTag(s,'heads-down')}),   // v1→2
  s => reorder(s, DICTATED_ORDER),         // v2→3
]
runMigrations(store, migrations)           // idempotent
View registry makes new views cheap›

Each view (Dashboard, Compare, Board, Matrix) is a module exposing render(state). Tabs are generated from the registry, so adding a view is additive, never invasive.

Data model: split the axes

The single most clarifying modeling change. Effort is a single-choice property; categories are multi-choice. Treat them differently.

Effort · pick one (exclusive)
● Small● Medium● Large

A task is exactly one size. The UI enforces it (radio behavior), so you can't tag both "Small" and "Large".

Category · pick many
CoordinationReviewPro-activeAlignmentLearning

Free combination, as today — but now structurally separate from effort.

Task shape

{
  id: 't_8f3k',            // stable, NOT the title (kills dup bug)
  title: 'Multi-tasking phase 1',
  effort: 'l',               // single axis
  categories: ['review'],     // multi axis
  status: 'open',            // open | done
  order: 0,
  createdAt, completedAt, notes
}
Why this matters for your views.

With effort as a real dimension, a Priority × Effort matrix (Eisenhower-style) and an effort-balanced Board become natural — you can finally see "am I overloaded on Large tasks this week?" at a glance.

UX upgrades

Same minimal aesthetic you steered us toward, but more capable and more forgiving.

New views worth adding

Board

Kanban by any dimension (effort, category, status). Drag between columns to re-tag. Generalizes today's Compare tab.

Matrix

2×2 of Priority × Effort. Drag a task to set both at once. Great for weekly planning.

Stack & tooling

Bias toward "no build step, double-click to run" — but escape the 1,400-line single-string trap.

Rendering REC
Alpine.js (15 KB, CDN) or Preact + htm (no build). Reactive without a toolchain. Keeps the single-file deploy.
Drag & drop
SortableJS — battle-tested, touch support, cross-list. Deletes ~120 lines of fragile DnD handlers.
Styling
CSS custom properties as design tokens (color/space/radius). Aligns with the project's existing token system in design-system/.
Persistence
localStorage + versioned schema + JSON export. Optional IndexedDB if notes/attachments grow.
Tests
A handful of vanilla unit tests for the data layer: migrations, AND-filtering, reorder. The logic that bit us most.
Optional build
Parent repo is already Vite. If this graduates beyond a toy, fold it in for modules + HMR — but only when justified.
Deliberately NOT adding:

React+Redux, a router, a component library, a backend. The whole charm is a personal, offline, instant tool. Complexity must earn its place.

Roadmap

Sequenced so value lands early and nothing requires a big-bang rewrite. Each phase is independently shippable.

Phase 1 · Foundation

Reactive core + single source of truth

  • Observable store + targeted render
  • TAGS config drives all chips/filters/forms
  • Versioned migration pipeline (retire the 4 ad-hoc flags)
  • CSS design tokens; light/dark
Phase 2 · Parity

Re-create today's features on the new core

  • Dashboard list, AND-filters, inline edit
  • Compare tab (multi-tag columns)
  • SortableJS reorder (incl. touch)
  • Split effort vs category axes in the data
Phase 3 · Delight

The stuff that makes it feel pro

  • Undo toast + Trash; keyboard shortcuts
  • Board view (Kanban by any axis)
  • Priority × Effort matrix
  • Quiet stats / insights strip
Phase 4 · Trust & polish

Won't lose your data, works for everyone

  • Export / Import JSON + auto-snapshots
  • Accessibility pass (ARIA, focus, contrast)
  • Unit tests on the data layer
  • Delete dead CSS / abandoned code paths
If you want only the highest-leverage slice:

Phase 1 alone removes ~80% of the friction we hit this session. Everything we struggled with — "edit in 5 places", "refresh to see it", focus loss, migration flags — is a Phase 1 fix.
